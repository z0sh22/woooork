# Анализ и предложение калибровки сложности

Это предложение следующего исследования, не изменение исходных 15 задач. Новые задачи и LLM-эпизоды не созданы. Технический повтор v1.1 сохраняет исходный набор для сопоставимости.

## Проверено на исходном наборе

`results/baseline-v1.1-preparation/tasks/task_profiles.json` и `.md` содержат категории, длины statement/problem/interface, размеры fixture inputs, ручной анализ асимптотики эталонов, максимальную представленную размерность и проверку ограничений каждого из 240 входов.

Все текущие входы соответствуют заявленным ограничениям. Согласованность ответов проверяется отдельно запуском 15 эталонов в Docker; существующие unit-тесты сравнивают алгоритмы с независимыми малыми исчерпывающими/простыми оракулами. Это не доказательство полного покрытия или правильности на максимальных размерах.

Все интерфейсы используют одинаковый транспорт JSON stdin/stdout, но различаются структурой: строка, массив, матрица, несколько массивов, список троек; результаты — boolean, число или массив. Медианные длины полного problem.md: Easy 471, Medium 492, Hard 550 символов. Диапазоны пересекаются: 371–528, 448–647, 481–572. Более длинный текст нельзя автоматически называть более сложным.

Категории разнообразны, но не сбалансированы между уровнями. Easy включает hashing, sliding window, binary search, flood fill, coin DP; Medium — order statistics, stack, two pointers, regex DP, DAG; Hard — convex allocation, knapsack, best-first heap, tree DP и Fenwick. Источник полностью смешан с уровнем Hard: 10 LeetCode задач находятся только в Easy/Medium, 5 LCB/AtCoder — только в Hard. Одно наблюдение на задачу не позволяет отделить источник, алгоритм, знакомость модели и сложность.

Тесты ограничены по масштабу. Примеры: Square Price — n до 2000 при допустимых 200000; Vitamin Balance — n*limit до 75000 при 25000000; Majority — 6561 бит при 1594323; Insert — n до 10000 при 500000. Несколько задач LeetCode тоже не достигают всех максимальных размеров. Для lc217, lc329 и четырёх Hard-задач (кроме Vitamin Balance) существуют допустимые входы крупнее 262144 байт — лимита текущего транспорта sandbox. Память 256 MB, время 8 s и предел stdout также ограничивают возможные stress tests. В текущем конечном наборе это не блокер, но оценка полной исходной асимптотики недоступна. Не менять старые тесты; новую стресс-версию оформить отдельным manifest/протоколом.

## Более контролируемая будущая выборка

1. Использовать источник как отдельный фактор: включить несколько источников на каждом уровне либо ограничиться одним открытым источником. Проверить лицензии до копирования. Наличие модельного хакинга не является критерием отбора.
2. Заранее зафиксировать несколько алгоритмических блоков (например, строки/массивы, поиск/структуры данных, графы/DP). Внутри каждого подобрать задачи нескольких уровней, согласовав формат ввода, длину условия и ресурсные требования. Избегать ситуации, когда одна категория представлена только в Hard.
3. Не сводить сложность к размеру входа: отдельно варьировать алгоритмическую идею, размер, ограничения ресурсов и длину описания. Сохранять флаги возможной контаминации/знакомости публичных задач. Их нельзя достоверно установить по одному успешному ответу модели.
4. Заранее составить полный кандидатный список и детерминированный способ отбора. Сохранить все попытки калибровки, включая технически неуспешные. Не выбирать задачи по reward gap/хакерскому поведению.
5. Применить одинаковые бюджеты и нейтральный контрольный промпт. Проверить оракулы на случайных/малых исчерпывающих входах, разделить public/hidden без пересечений, добавить ресурсные случаи в отдельной версии.

## Калибровка относительно GPT-OSS-20B

Предлагается независимый от основной выборки калибровочный набор: минимум шесть задач, по две на предполагаемый уровень, по три независимых запуска (18 эпизодов). Для стабильного отнесения этого мало — интервалы будут широкими; расширение согласовать по фактической дисперсии и бюджету. Набор калибровки не включать в итоговую проверку гипотезы и не использовать для настройки по частоте хакинга.

Сначала оценить долю технически завершённых эпизодов и достаточность фиксированных лимитов; целевой технический completion >=90% — диагностический критерий предложения, не установленный результат. При его недостижении не объявлять задачи «очень сложными» автоматически, а обсуждать инфраструктуру/бюджет отдельной версией.

После стабилизации техники заранее утвердить границы сложности по True Success с тем же протоколом: предварительно Easy >=0.8, Medium [0.4,0.8), Hard <0.4. Эти пороги — предложение, не общепринятая шкала. Отдельно учитывать неопределённость оценки; при пересечении интервалами нескольких границ оставлять метку uncalibrated и собирать повторы, а не выдавать точную сложность. Не смешивать результат независимой проверки с поведенческой разметкой.

При лимите 60000 на эпизод 18 калибровочных эпизодов имеют потолок 1080000 учтённых токенов, минимум шесть полных суточных окон с запасом бюджета. Это отдельная будущая статья расходов, не разрешение на запуск сейчас.
