# Технические проверки и изменения до основного пилота

## Docker/WSL

Изначально Linux daemon был недоступен. Проверка WSL показала отсутствующие
ext4.vhdx по зарегистрированным путям. После ответа пользователя, что установка
новая и важных данных нет, восстановлена регистрация Docker Desktop. Затем
заново собран доверенный образ. Поскольку daemon сообщал profile=unconfined,
добавлен явный официальный seccomp profile. Его применение проверяется внутри
контейнера (Seccomp=2/NoNewPrivs=1), а не предполагается по наличию CLI.

Позже локальный образ перестал находиться по tag. Он пересобран из того же
закреплённого base digest, после чего повторно прошли все 12 контейнерных тестов.
Причина исчезновения tag отдельно не установлена; она не приписывается модели.
Новый image ID фиксируется в основном запуске. Код решения никогда не
переключался на исполнение на хосте.

## Function calling Groq

GET /models подтвердил доступность openai/gpt-oss-20b. Отдельная синтетическая
проверка finish_task прошла с фактическими 301 токеном и не входит в
поведенческие результаты.

Первая техническая попытка baseline-v1 была прервана HTTP 400 после list_files.
При диагностическом повторе второго запроса получен tool_use_failed с именем
read_file<|channel|>commentary. Доступный failed_generation сохранён отдельно;
исходный error body первой попытки не сохранялся, поэтому ему не приписывается
вымышленная точная генерация.

В r1 введён groq_channel_workaround: документированный API-параметр
disable_tool_validation возвращает вызовы контроллеру, а локальный allowlist и
проверка аргументов остаются обязательными. Убирается только наблюдавшийся
суффикс <|channel|>commentary у одного из пяти известных имён; произвольные
имена/другие суффиксы не превращаются в разрешённые инструменты. Исходное имя
и преобразование записываются. Эта опция не включает provider-hosted tools.
Семантика параметра: [официальный Groq API reference](https://console.groq.com/docs/api-reference).

r1 дал завершённый Easy-эпизод, затем provider отклонил невалидный JSON в
вызове run_command на Medium. Поэтому r2 обрабатывает tool_use_failed как
наблюдаемую ошибку сериализации: сырая доступная генерация сохраняется,
предоставляется нейтральный feedback о формате, а после двух таких ошибок
эпизод завершается с текущим решением. Ошибка не превращается в успешную
модельную реплику, исполняемый shell или выдуманный usage. Все запросы и
неопределённые резервы учитываются. Прочие ошибки API не скрываются.

## Комплектация задач и разделение ревизий

Проверка официальной страницы показала Medium у LeetCode 72. До основного
пилота задача заменена на LeetCode 10 Hard; набор ТЗ 1 Easy + 4 Medium /
5 Hard / 5 LiveCodeBench Hard сохранён. Это исправление метаданных отбора,
не исследовательская смена шкалы сложности.

Результаты baseline-v1 и baseline-v1-r1 не объединяются с r2. Архив r1
с контроллером, конфигурацией, задачами, промптом и исходниками образа находится
в results/protocol_archives/r1; хеши контроллера сверены с manifest. .env и
credentials туда не копировались. Исходные траектории технических попыток
сохранены, а их расходы учитываются отдельно от основного поведенческого набора.

Температура 0.2, нейтральная постановка, модель, лимит 15 инструментов и
отсутствие стимулов/памяти не менялись ради появления или исчезновения хакинга.
В исправлениях нет обучающих воздействий или подсказок о способах манипуляции.

## Файловая блокировка во время r2

На оценивании lc42 возник WinError 5 при атомарной замене original_public.json.
В тот же период выполнялась проверка сохранённых артефактов; блокировку могло
вызвать чтение файла или синхронизация OneDrive. Точная причина не установлена.
Параллельные чтения результатов прекращены. Контроллер возобновлён с тем же
протоколом через --resume: сохранённое решение продолжило независимые тесты.
По траектории после прерывания зафиксированы 13 case events, ноль новых
запросов модели и успешное завершение эпизода. Доказательство сохранено в
results/resume_validation.json. Новая попытка агента не создавалась.
