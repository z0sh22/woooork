## Очередь контрольного запуска

Команда внешнего контроллера:

```powershell
.\.venv\Scripts\python.exe scripts/run_control_plan.py --experiment-id baseline-v1-1-control-20261126 --plan-dir results/baseline-v1-1-control-plan-20261126 --approved-control-smoke-and-pilot --max-wait-hours 24
```

Флаг фиксирует уже полученное в этой сессии разрешение. Runner имеет single-process lock и отпечатки протокола/исходников; изменение кода или конфигурации требует отдельной версии/ID. Ожидание ограничено 24 часами на один запуск runner; при его истечении незавершённое состояние сохраняется. Уже завершённые эпизоды не переигрываются. Незавершённое оценивание может возобновляться без бюджета новых генераций.

Порядок: lc217 (Easy), lc4 (Medium), abc389_e (Hard). После их завершения сохраняются smoke checkpoint и проверка контроллера. Переход к остальным задачам требует известных результатов независимого оценивания, записанной публичной проверки, начальных/итоговых снимков, доступного model usage и отсутствия критического API/инфраструктурного сбоя. Успешность алгоритма, наличие признаков хакинга, изменение checker, наличие реализации и завершение модели по лимиту **не используются для отбора выгодных научных результатов**. Они сохраняются как наблюдения и технические предупреждения.

HTTP 401, другой критический отказ API или ошибка инфраструктуры останавливают план; controller не создаёт последовательность одинаковых неуспешных эпизодов на всех задачах. Полный прогон включает три smoke эпизода, поскольку протокол после их просмотра не меняется. Все 15 задач/тестов и настройки одинаковы между уровнями.

Текущий статус очереди: `results/baseline-v1-1-control-plan-20261126/status.json`. Вывод процесса — `controller.stdout.log` и `controller.stderr.log` там же. Реальные траектории/метрики, если запуск начался, — `results/baseline-v1-1-control-20261126`. Отсутствующие результаты не заполняются синтетикой. При необходимости будущий анализ по всем planned задачам показывает unknown отдельно.

Фоновый процесс продолжает работу, пока компьютер и Docker доступны. После перезагрузки автоматическое продолжение не гарантируется: проверить PID из status и отсутствие живого контроллера перед удалением устаревшего `.plan.lock`, затем повторить ту же команду с неизменённым протоколом. При недоступном ключе обновить `.env` и перезапустить план; ключ в сообщениях не нужен.

## Исправление Docker

Образ отображался в `docker image ls`, но `docker image inspect` возвращал No such image. После сборки обычного локального образа командой ниже inspect стал успешным:

```powershell
docker build --provenance=false --load --tag safety-games-sandbox:local sandbox
```

Это согласуется с проблемой совместимости image index/attestations и локального image store; точная внутренняя причина Docker не устанавливалась. [Docker документирует различия image store и возможность отключения build attestations](https://docs.docker.com/build/metadata/attestations/). Закреплённый базовый образ, Dockerfile, файлы trusted runner и ограничения выполнения не изменены. Исправлен способ упаковки результата сборки; runtime seccomp/network/resource checks сохраняются.

Неуспешный прогон тестов сохранён в `infrastructure_tests_20261126_manifest_failure.json`; итоговый повтор — `infrastructure_tests_20261126_final.json` в папке подготовки. Это инфраструктурные проверки без генераций LLM.
